아래로 스크롤하며 기업의 데이터가 맥락을 가지게 되는 여정을 확인해 보세요.

01 · 정형 데이터

데이터베이스

왼쪽 받침의 다섯 개는 Google Cloud의 First-Party DB이고, 점선 받침의 두 개는 Databricks, Snowflake 같은 3rd-Party 데이터베이스입니다.

Knowledge Catalog로 올라가는 건 데이터 원본이 아닌 메타데이터뿐이고, 조회와 계산도 원본 DB에서만 이루어집니다.

02 · 비정형 데이터

끄적인 메모가 데이터가 되기까지

절차서, 규정집, FAQ, 그리고 담당자 머릿속의 노하우는 형식과 모양이 제각각입니다. 데이터베이스에 바로 삽입할 수 없기 때문에, 일정한 형식으로 성형합니다.

Gemini가 OKF 문서 초안을 만들어주면, 게이트가 근거 문서와 관계 대상을 점검합니다. 이후 담당자가 승인하게 되면, status가 stable이 됩니다.

03 · Knowledge Catalog

데이터 카탈로그

왼쪽 서랍은 컬럼과 스키마가 들어 있는 기술 메타입니다.

오른쪽 서랍은 정의와 규칙 등이 들어 있는 비즈니스 메타입니다. OKF 문서는 여기에 저장됩니다.

04 · Graph

데이터 사이의 연결고리

BigQuery Graph와 Spanner Graph는 이미 있는 테이블 위에 관계만 정의합니다. 고객, 주문, 반품, 배송, 이탈 카드를 실로 엮어 두는 셈입니다. 데이터를 복사하지 않고 처리합니다.

05 · MCP

요청과 응답

AI 에이전트는 MCP 서버로 요청을 보냅니다. MCP 서버는 그 요청을 도구 호출로 바꿔 카탈로그에 묻고, 받은 답을 다시 에이전트에게 돌려줍니다. 빨간 점선 하나를 따라 요청은 카탈로그 쪽으로 내려가고, 응답은 에이전트 쪽으로 올라옵니다.

도구는 세 개를 차례로 씁니다. search_entries로 찾고, lookup_entry로 하나를 자세히 보고, lookup_context로 최대 10개 엔트리를 YAML이나 JSON 한 묶음으로 받아 갑니다.

한 번에

질문 하나가 지나가는 길

“지난 분기 우수 고객 이탈률이 왜 올랐지?”라고 물으면 에이전트는 네 가지를 알아야 합니다. 데이터가 어디 있는지, ‘우수 고객’이 무엇인지, 무엇을 이탈로 보는지, 왜 올랐는지.

  1. 어디에 있지? 카탈로그의 기술 메타가 BigQuery 테이블 위치를 알려 줍니다.
  2. ‘우수 고객’이 뭐지? 매출 상위이면서 반품률 20% 미만인 고객입니다.
  3. 무엇을 이탈로 보지? 문서에서 만든 OKF 파일에 기준이 있습니다.
  4. 왜 올랐지? 그래프 판에서 고객부터 이탈까지 이어진 길을 따라갑니다.
  5. lookup_context가 이 넷을 한 묶음으로 에이전트에 건넵니다.
